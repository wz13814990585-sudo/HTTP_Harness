# P01 implementation report

Date: 2026-09-22 (Australia/Sydney)

Status: **complete** for the P01 exit gate. The implementation provides durable
Run admission/query/cancellation and database foundations. It does not yet run a
model, execute a tool, expose events, manage files/artifacts, or provide MCP.

## Delivered behavior

- Development bearer-token authentication with explicit `runs:read` and
  `runs:write` scopes. Missing/invalid tokens fail 401; revoked scope fails 403.
- Subject/tenant-scoped `POST /v1/runs`, `GET /v1/runs/{run_id}`, and
  `POST /v1/runs/{run_id}/cancellations`.
- PostgreSQL-scoped request idempotency using a unique constraint and
  `INSERT ... ON CONFLICT DO NOTHING`; same fingerprint replays the saved 202
  envelope and a changed fingerprint returns 409.
- A single `RunController` for Run transitions and admitted Action state changes.
- Atomic Run/Event/Job/Budget admission and cancellation transactions.
- PostgreSQL job claiming with `FOR UPDATE SKIP LOCKED`, leases, and epochs.
- A ready-to-running Action CAS plus unique Action attempt ledger, proving duplicate
  wakeups do not become duplicate dispatch admission.
- SQLAlchemy models and an Alembic migration for Run, Action, ActionAttempt,
  ModelCall, Event, Job, Idempotency, and Budget records.
- Fail-closed startup: without PostgreSQL configuration the health endpoint remains
  available, authenticated Run mutation returns 503, and no in-memory/SQLite
  authority is substituted.

The ASGI runtime currently advertises exactly three target operations. The other
20 operations in the target contract remain absent from runtime OpenAPI.

## Failed attempt retained

The first real PostgreSQL run produced 1 pass and 9 failures. SQLAlchemy had no ORM
relationship dependency between the independently added Run and Budget objects, so
it attempted the Budget insert first and PostgreSQL correctly rejected the foreign
key. The fix explicitly flushes the Run aggregate root before adding its dependent
Event/Job/Budget rows while retaining the same encompassing transaction. The next
targeted run passed 10/10, and the final full run passed 63/63. The constraint was
not removed or deferred to make tests pass.

## Boundaries and next safe action

- AT-010 proves local dispatch admission is deduplicated; it does not claim a remote
  effect is exactly-once. No executor runs in P01.
- The pre-commit and snapshot/event tests use deterministic exception injection at
  the transaction boundary, not an operating-system kill of PostgreSQL.
- Development tokens are local-mode authentication, not production OIDC.
- Docker daemon remains unavailable; sandbox validation is still blocked until P04.
- Model credentials and MCP endpoint configuration remain absent; no live calls were
  attempted.

Next: P02 should introduce the Capability registry and unified ActionGateway, then
managed workspace files and immutable artifacts, while continuing to route all
state changes through this RunController.
