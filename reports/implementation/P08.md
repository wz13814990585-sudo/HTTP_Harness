# P08 implementation report

Date: 2026-09-22–23 (Australia/Sydney)

Status: **local implementation complete; stage exit blocked by environment; not
a release candidate**. AT-066 and AT-067 have local execution evidence. AT-065
and AT-068 have tested recording/aggregation machinery but no real four-arm
model run; they remain `blocked_environment` and unrun.

## Implemented so far

- A strict four-arm evaluation driver with one shared controls object and
  predeclared oracle per case. Each attempt emits a fsynced raw JSONL row;
  failures, timeouts, and blocked outcomes are retained. A separate off/on
  ablation driver prevents combining optional features with the HTTP/MCP axis.
  Provider-reported token counts are accepted only with an explicit source;
  missing usage stays null, not estimated. `eval/summarize.py` keeps all outcomes
  in the denominator and counts false completion separately. Four-arm execution
  now uses a fixed-seed, per-case rotating order: across four cases each arm
  occupies each position once. Raw rows record case/arm position and seed.
  The summarizer reports each arm separately, including denominators,
  provider-usage sample counts and p50/p95 with sample counts. Missing or
  duplicate case-arm rows set `design_complete=false`; its CLI exits 2 rather
  than silently treating a truncated raw file as a complete experiment. A
  nominally complete arm set also fails the design gate if controls, case
  oracle/hash/index, seed/position or labeled/unlabeled rows disagree.
  The independent ablation recorder now counterbalances off/on order by case
  and seed. Its summarizer requires both conditions for each case and a
  consistent feature, controls, oracle and position; missing/mixed data or
  unlabeled records make the CLI exit 2. Both condition denominators are
  reported separately. An unrecognized raw design is not a successful report.
  Both recorders re-hash their shared controls after every executor call and
  stop immediately if mutable settings or budgets were changed under the
  supposedly fixed experiment label.
  A concrete opt-in skills ablation executor now uses this recorder: both
  conditions run the same native echo through durable Runner/ActionGateway,
  while only the on condition loads a SHA-pinned allowlisted guidance file.
  Its local PostgreSQL/mock-Responses integration test confirms on/off
  context differences, committed echo Actions and a complete raw design;
  changing the skill after pinning fails before a Run/model call. The
  `eval/run_live_skills.py` entrypoint is available only with explicit real
  model configuration. No live benefit has been measured.
  The summarizer additionally checks every row's explicit model revision,
  model-settings hash, capability revision, policy revision and fixture
  identifier, across four-arm, ablation and task-suite designs. A mixed or
  missing value makes the design incomplete even if the top-level controls
  hash is unchanged. This is an audit consistency gate, not a cryptographic
  signature on raw data. It now also rejects non-finite timeout controls,
  boolean counts, estimated token counts mislabeled as unavailable, invalid
  usage source labels, and verified-completion claims with no raw
  oracle/evidence. A labeled row missing non-completion evidence makes its
  dataset design-incomplete instead of silently auditable.
  All recorders now include explicit model/capability/policy revisions,
  model-settings/fixture hashes, and the executor's committed ModelCall,
  Action, Artifact IDs and committed event-sequence range where available. They export
  references, not raw potentially sensitive tool bodies.
- A native Responses `function` tool catalog is derived from the same scoped
  Capability input schemas as the HTTP-semantic arm. A completed `function_call`
  is decoded to an untrusted `HttpOperation`; it is never dispatched by the
  provider. The Runner persists the full call (including `call_id`) before the
  common ActionGateway binds and executes it. Unknown tool names, invalid
  arguments, forbidden extra fields, duplicate call IDs, and path separators
  are rejected. Multiple complete function calls are supported with a bound;
  they are admitted individually by the same Runner budget and gateway. The
  two arms receive the same task context without a duplicated compact catalog;
  the function arm's final-answer schema excludes HTTP operation fields, so
  only their model-facing operation interface differs. This is a local mock
  Responses test, not a live model comparison.
- A controlled four-arm PostgreSQL integration test now exercises both
  model-facing surfaces against native echo and an official SDK/in-process MCP
  Server echo. It holds goal, model name, output limit, scopes and input value
  constant, confirms all four Actions succeeded through the gateway, and
  compares identical structured echo observations. Model responses use
  MockTransport; MCP is local in-process, so this proves wiring/equivalence
  for one read-only case, not AT-065 live experimental results.
  A second four-arm test reaches the same official MCP echo fixture in a
  separate Uvicorn OS process over real loopback TCP/HTTP. Both MCP Actions'
  stored structured results contain the child process PID. The test-only
  transport creates a fresh connection context for discovery and invocation;
  the first attempt reused a one-shot async context and left both MCP Actions
  `outcome_unknown`, which was a fixture error. The corrected test passed on
  real PostgreSQL. It still uses mock Responses and unauthenticated local
  HTTP, not an independent HTTPS/OAuth endpoint or live model benchmark.
- An opt-in `eval/run_live_echo.py` entrypoint now assembles a real Responses
  provider, issuer-pinned OAuth MCP adapter and dedicated read-only echo Runs
  for all four arms. It writes immutable raw rows via `ExperimentRunner`,
  judges the oracle from a succeeded Action, and reads token usage from
  persisted ModelCalls only when reported by the provider. The operator must
  supply a migrated, dedicated PostgreSQL database and an independent HTTPS
  MCP echo endpoint with client credentials. Its frozen fixture has four
  distinct echo-message inputs, counterbalanced across 16 case-arm Runs;
  this remains one read-only capability family, not a multi-capability task
  suite. One local-PostgreSQL test runs all 16 combinations with MockTransport Responses
  and an official in-process MCPServer. It is not a real-model benchmark.
  The executor now discovers and validates the remote echo input/output contract
  before creating any campaign output, Run or ModelCall; it rejects a remote
  tool that cannot accept the canonical 1–100-character message domain or
  does not explicitly promise a required string `message` result, and
  pins the discovered capability revision. Matching native/MCP arms expose
  the same canonical model-facing ID, revision, function name, resource
  address, input/output schemas, descriptions and successful observations.
  A trusted evaluation-only binding maps the already-admitted canonical Action
  to the preflight-pinned remote capability; the committed MCP result retains
  its original protocol wrapper, source metadata and RPC fingerprint.
  Capability drift aborts the experimental design, not just
  one task row. A separate-process loopback test checks both model-facing
  schemas and the second-turn observations across all four arms. This still
  does not establish live-model or independently hosted MCP results.
- A separate opt-in `eval/run_live_tasks.py` entrypoint now has three frozen,
  distinct read/transform/artifact cases: uppercase, nonempty-line count, and
  integer sum. Operator fixture writes go through ActionGateway in separate
  implicit Runs; the model catalog contains only `workspace.file.read` and
  `artifact.create`. Each task Run is graded against actual stored Artifact
  bytes/media type plus successful read/create Actions. A suite-specific raw
  JSONL recorder holds the predeclared size/hash and all outcomes; its
  summarizer rejects missing/duplicate/mixed cases. One PostgreSQL + external
  Blob test completed the three tasks through nine mock Responses calls and
  six task Actions; a second test demonstrated that a Run can succeed at the
  generic CompletionGate while the independent task oracle correctly counts
  a wrong artifact/no-read as false completion. These are mocked-model local
  tests, not live-model scores or a broad benchmark.
  The entrypoint now checks actual read/create revisions, the complete frozen
  fixture hash, actor scopes and policy revision before seeding files; each
  task Run rechecks them. Drift is a design error, not an ordinary failed
  task row. Four parameterized PostgreSQL negative cases confirm no Run,
  Action or model call for mislabeled controls. Older negative-oracle tests
  were corrected to record their real capability and fixture identities.
  A third PostgreSQL test confirms that creating the correct artifact in the
  same model turn as the file read is still a false completion: the read result
  could not have informed that proposal. The raw summarizer now rejects a
  `verified_completion` flag contradicted by the recorded outcome and evidence.
  If the task evaluator itself stops while its durable Run is still running,
  it now moves that Run to `blocked` with an `evaluation_stopped` reason before
  recording the raw row. This prevents another worker from silently advancing
  a stopped evaluation without falsely asserting that prior local effects
  were undone. Both task and echo paths label provider timeouts as timeout
  outcomes instead of generic failures. PostgreSQL tests cover a scripted
  provider error and an `httpx.ReadTimeout` cause; no live provider was used.
  Both evaluators now recheck the campaign deadline after every synchronous
  Runner advancement. A committed Run that returns after the deadline remains
  truthfully succeeded in PostgreSQL but is scored as a timeout, not an
  on-time evaluation success. The raw row includes that Run status and
  committed evidence. The summary separates late evidenced claims from
  false completion claims; it does not claim to preempt an in-flight call.
- Both OpenAI Responses surfaces now reject a response whose status is not
  `completed`, even if it contains parseable partial text. A partial model
  response cannot reach ActionGateway.
- CI evidence now separates `evidence_consistent` from `release_ready`. The
  normal gate requires the JUnit test inventory, runtime AT map, and all 68
  design-spec IDs to agree. A tag-triggered release gate additionally refuses
  any blocked, failed or unrun acceptance case; the current three known
  blockers make it exit 2. The non-tag workflow passed on GitHub-hosted runs
  `35765430976` and `35766185495`; the tag-only strict release branch was
  therefore correctly not invoked. The latter run used Node 24 actions pinned
  by full commit SHA.
- `/readyz` distinguishes real DB connectivity from missing model, isolated
  broker, blob, and MCP configuration. `/metrics` is scope-protected and labels
  only route templates, methods and status classes. HTTP responses carry a
  validated/generated W3C traceparent. Metrics are process-local, not execution
  truth. An optional OpenTelemetry SDK OTLP/HTTP exporter now emits
  route-template HTTP spans only when an admin-configured HTTPS (or local
  loopback HTTP) endpoint is present; redirects and credential-bearing URLs
  are rejected. A real localhost receiver accepted protobuf spans, but no
  external collector or distributed trace has been tested.
- Offline DB+immutable-blob backup and empty-target restore helpers, with
  checksums and no worker startup. The test restored an active blocked Run,
  terminal Run, Blob and `outcome_unknown` unsafe Action into a second real
  PostgreSQL database. The unsafe Action's ready-to-running CAS still refused
  redispatch. The script requires writers to be quiesced before backup.
- A test-only localhost HTTP effect service now commits a publication to an
  independent ledger and closes the TCP connection before its first response.
  Against real PostgreSQL, an unsafe Action became `outcome_unknown`/blocked;
  a rebuilt controller could not redispatch it; querying the remote ledger
  reconciled exactly one observed publication. This is genuine socket-level
  response loss, but the test invokes the RecoveryCoordinator with a
  pre-admitted Action; it is not a full model-to-ActionGateway-to-publisher demo
  or an independent production service.
- CI now separates static/unit/contract checks from PostgreSQL/Docker integration,
  migration round-trip/drift and runtime contract checks. The integration job
  now emits JUnit and runs an acceptance execution gate: every passed AT's
  mapped tests and each blocked AT's partial tests must be collected and pass;
  only explicitly mapped live blocked tests may skip. JUnit is retained as
  a CI artifact. GitHub-hosted run `35765430976` passed the integration job
  and retained that artifact; local commands remain reported separately.
- A development-only Compose topology now pins Python 3.12.14 and PostgreSQL
  14.18 multi-platform image digests, installs the locked app and optional MCP
  adapter, then runs a one-shot migration before separate API and worker
  containers. The API binds host loopback only; PostgreSQL has no published
  port. App containers run as UID 10001 with read-only roots, dropped caps,
  no-new-privileges and no host/Docker-socket mounts. This does not provide a
  production identity provider or isolated broker. The initial Compose smoke
  predated the two ledger-backed local worker writes documented below.
  Model credentials are passed only to the worker, not the API container;
  API-local readiness therefore reports model configuration missing.
  A self-cleaning smoke project with fake model configuration verified the
  migration, DB-backed readiness and authenticated capability catalog; it
  never submitted a model Run. GitHub-hosted run `35765430976` repeated and
  passed that smoke with the same non-live boundary.
- Run admission now persists an admission-time scope ceiling; resumed actor
  scopes are intersected with it and child Runs cannot mint scopes their
  parent lacked at admission. This ceiling is **not** an authentication source:
  a future worker must still resolve the actor's current scopes from a trusted
  provider. The migration assigns legacy Runs an empty ceiling. ModelCall
  begin/response/failure/processing transactions can be fenced to an
  `advance_run` lease; a reclaimed lease rejected an old worker's delayed
  model response while allowing the new worker's attempt. The Runner/Gateway
  are not yet wired as a safe automatic worker, so this remains a prerequisite,
  not a completed deployment claim.
- The same `advance_run` job lease now fences ActionGateway admission,
  ready-to-running transition and result commit for native read-only Actions.
  A stale worker cannot create another Action or commit its late result; a
  successor cannot redispatch an already-running Action. Lease-bound MCP and
  non-read-only effects currently fail explicitly before Action admission,
  because their adapter receipts are not yet fully lease-aware. Context
  snapshots pin the effective scope fingerprint; after revocation, resuming
  the same turn raises `migration_required` instead of reusing a broader
  model-facing context. Older snapshots without the pin also fail closed.
  This was the prerequisite for the bounded worker below.
- A bounded `RunWorker.run_once()` now claims a durable `advance_run` job,
  resolves the tenant/subject's **current** actor through an injected trusted
  resolver, renews the lease during a blocking model call, advances one model
  turn, and either completes or defers the job. Provider unavailability gets a
  durable delayed wake-up; scope-fingerprint incompatibility blocks the Run.
  A lease-specific unsupported-effect error now reaches the worker rather than
  being mistaken for a committed Action failure: at this earlier slice, leased
  MCP and writes blocked before Action admission. Real PostgreSQL tests cover two-worker
  handoff, heartbeat beyond the original lease, transient provider recovery,
  identity mismatch, scope revocation, and a rejected write. This is a
  **library worker for the native read-only slice**, not a deployed worker
  process or general side-effect scheduler. No production actor resolver is
  configured. Context/skill pin commits and all Runner budget
  reservation/settlement/release calls are now fenced to the same Run lease;
  a reclaimed worker cannot write those records either.
- An opt-in `hnh-dev-worker` process entrypoint now assembles the same
  PostgreSQL-backed native read-only Runner as the API's local development
  configuration. It requires a local development token and configured model;
  missing values fail at startup. One real PostgreSQL test submitted a Run
  through the ASGI API and processed it with a second composition. Another
  launched the worker as a **separate OS process** against the same temporary
  PostgreSQL database and a localhost mock Responses HTTP service; the
  CompletionGate committed the Run as succeeded. This demonstrates a
  single-node development topology only, not a live OpenAI request, real MCP
  service, production identity/revocation integration, supervisor, or
  general write-capable worker.
- A second process-topology test launched both Uvicorn API and the worker as
  independent OS processes. A real localhost HTTP client observed the initial
  queued Run and its later succeeded state across the two processes, backed by
  real PostgreSQL. The model endpoint was again a localhost fixture, not a
  live provider. The test explicitly terminated only its own child processes.
- A controlled worker-kill chaos test terminated the worker process after it
  sent a model request but before response persistence. After the three-second
  test lease expired, a successor process reclaimed the same Run, made a new
  model attempt, and completed once. PostgreSQL held two model attempts and
  zero Actions; no side effect was replayed. The model HTTP service was a
  fixture, so this is process/lease recovery evidence, not live-model billing
  or remote effect recovery.

## Ledger-backed local worker effects

The bounded worker now admits exactly two native local effects under a claimed
Run lease: `artifact.create` and conditional `workspace.file.write`. Before
dispatch, ActionGateway binds the complete model proposal, authorizes it,
records one Action and freezes `action:{action_id}` as the resource business
key. The resource transaction stores its idempotency receipt alongside the
Artifact/file version. If the Action result transaction is lost after that
commit, a successor may reclaim only a `local_transactional` Action in this
allowlist, with a newer lease epoch and the identical business key. The prior
attempt remains in the ledger as `outcome_unknown`; the new attempt re-enters
the resource method, whose PostgreSQL idempotency record returns the original
result instead of applying the write twice. A stale worker cannot commit its
old result. A different business key is rejected.

Real-PostgreSQL tests covered a worker's conditional file creation followed by
evidenced Run completion, a committed Artifact whose Action receipt was lost,
and a committed file write whose receipt was lost. Recovery retained one
Artifact / file revision 1. The worker's `HNH_BLOB_ROOT` is now wired to the
same FileBlobStore as the API; a separate integration test read the
worker-created Blob through the API and verified that bytes were not stored
inline in PostgreSQL. The Compose worker mounts the same named Blob volume as
the API. Its self-cleaning `bash scripts/check_dev_compose.sh` smoke passed:
migration, DB/API/worker health and authenticated catalog; no model request
was made.

This is **not** a general write-capable scheduler. `execution.session.create`,
Python cells, MCP and remote effects still fail before leased Action admission.
PostgreSQL idempotency does not make the Blob store transaction atomic with
PostgreSQL, and it cannot prove exactly-once at external APIs. The narrow
local cancellation window below now has receipt-based confirmation; Blob loss
and remote effect cancellation still need separate evidence handling.

When cancellation wins after one of these local resource commits but before
the Action result commit, `--cancel-only` reads the existing resource
idempotency row. The kernel checks the original Action business key, request
fingerprint, actor, source Action, Artifact hash/size and response shape. It
then records an Action success and `action.reconciled_local` event under the
current `cancel_run` lease before confirming `Run.cancelled`. This path never
calls ResourceStore.write_file/create_artifact or creates a second HTTP
exchange. A missing or mismatched row leaves the Action RUNNING and the Run
CANCELLING. Two success and two negative fault-injection cases passed on real
PostgreSQL; an expired `cancel_run` lease could not reconcile, and the old
`advance_run` lease could not overwrite the reconciled result.
This does not prove a remote side effect stopped or that a Blob file still
exists if its external storage has been lost.
