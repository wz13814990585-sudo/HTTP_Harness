# 研究结论：哪些事实应当进入架构

## 1. MCP 官方确实向普通 HTTP 基础设施靠拢，但没有移除 JSON-RPC

2026-07-28 已正式发布；本次 `specification/latest` 指向这一版本。协议核心变为每请求自描述；不再把执行上下文藏在协议连接会话里。本文采用其“显式资源句柄”的思想，而不照搬整个 RPC 层。来源：R01、R02、R04。

HTTP headers 是可被网关读取的镜像，具体绑定仍以 body 为源并校验一致性；这不是允许模型任选一个 header 就取得权限。`Mcp-Method` 与有适用条件的 `Mcp-Name`、`x-mcp-header` 的参数映射值得借鉴，但本项目优先使用 URI 和方法表达资源操作，避免重复编码。来源：R03、R05。

MRTR、Tasks 与缓存分别提示三种工程能力：可持久化的补充输入、可轮询的长任务、稳定且按授权范围隔离的能力目录。对应到本项目分别是 InputRequest、Action/Run、Capability Catalog，而不是把这些术语强塞进 HTTP 标准。来源：R06、R07、R08。

特别重要：新 MCP 传输层移除了旧 SSE 事件 ID / Last-Event-ID 重放。自己的 Run 事件服务可以保留持久化 SSE 重放，但不能宣称它来自新 MCP，也不能把新的 MCP SSE 当成持久化队列。来源：R09。

## 2. 现代 Harness 的机制可以融合，运行引擎不能层层套娃

参考 OpenAI Runner 的小循环、LangGraph 的持久检查点、ADK 的事件提交边界、Microsoft 的分层扩展，以及 Deep Agents / DeerFlow 的上下文和执行环境。每个项目只借鉴所需机制，不把所有 SDK 引为运行依赖，不让两个独立引擎同时拥有同一 Run 的最终状态。来源：R11、R13–R18。

本方案选择自行实现一个有限状态机内核，而不是完整图工作流产品。若未来需要跨区域、任意长时间工作流和更复杂的工作流运维，应该另行评估成熟耐久引擎，由它接管调度所有权；不能在现有内核外面再套一个互相重试的工作流循环。

## 3. 朋友的项目分别提供什么，不提供什么

Elastik 的地址化与 raw/derived 分离进入产物和上下文设计。pythond 提供存活的 Python 会话模型，不提供满足本项目威胁模型的隔离；curldb 提供通信记录模式，不提供端到端安全恢复；TypeSafe 提供决策建议，不替代权限判定。来源：U01、R19–R22。

本项目不必强依赖这些包；可以先实现对应 Port，再采用维护者 SDK 或项目作为 Adapter。这样既保留来源和理念，又能在项目维护状态变化时替换实现。

## 4. 必须修正的早期直觉

“HTTP 比 MCP 更符合模型读取方式”是实验假设。MCP 线协议通常由 host/SDK 处理，模型可能仅看到工具名称、说明和 schema。不能把所有 JSON-RPC 字节都算成模型 token，也不能故意让 MCP 基线手写 JSON-RPC。来源：R12。

“只要 HTTP 200 就成功”“403 就请求审批”“500 一律重试”“有 ETag 就实现调度”“存了报文就能重放恢复”都不能作为实现规则。状态、错误、权限、并发与恢复必须由明确的应用契约决定。

`Idempotency-Key` 可以用作本项目契约，但本次查询对应 IETF 文档仍是过期草案。真正的幂等保证来自持久化键、请求指纹、唯一约束与下游约定，不来自这个 header 的名字。来源：R23、R25。

## 5. 架构结论

采用 **HTTP 资源契约 + 单一持久化内核 + 受控执行网关 + 可替换适配器**。主链条不依赖 MCP；MCP 仅作为可选兼容边界。模型既能通过 HTTP 语义操作使用能力，也能通过从同一能力定义生成的原生工具接口使用能力，保留公平评估两种模型界面的可能性。
